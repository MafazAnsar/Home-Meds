# Stage 1 — Technical reconnaissance and implementation plan

**Status:** Proposed implementation plan; no application changes yet  
**Branch:** `homemeds-2.0-architecture`  
**Baseline:** Commit `330d88c9bb423494d0378e00fcabe82446b4c271`

## 1. Verified current structure
- `index.html` — UI markup and inline event handlers.
- `src/app.js` — UI rendering, domain operations, and IndexedDB persistence in one file.
- `src/styles.css` — styles.
- `package.json` — Capacitor dependencies, but no scripts, test framework or committed lockfile.
- `capacitor.config.json` — app ID, web directory and app name.
- `.github/workflows/build-homemeds2.yml` — CI assembles `www`, installs packages, generates Android project, syncs and builds signed debug APK.
- Android native project is generated by the workflow and not committed in this branch's current tree.
- IndexedDB database name `home-meds-2`, schema version 4; stores include medicines, doseEvents, profiles, stockTransactions, doseAudit, inventoryItems, prescriptions, doctorProfiles and inventoryTransactions.

## 2. Findings and constraints

### 2.1 Current coupling
The current JS combines database access, rendering, UI event binding, business operations, migration logic and user prompts. Extracting modules must be incremental and behaviour-preserving.

### 2.2 Data transition
The user confirms the existing prototype contains no real user data. Demo seed records are not data to migrate. We can transition to a clean database foundation without a record-migration project. However, schema migrations, integrity validation, backup/export and recovery remain requirements for future data.

### 2.3 Build pipeline
The workflow generates Android from Capacitor on CI. Any native plugin must be compatible with this generated-project workflow and installed/configured during CI. Preserve signing secrets and signing configuration.

### 2.4 Test gap
No test framework or test scripts were found in the package manifest. Establish repeatable test infrastructure and gates. An APK build alone does not verify application behaviour.

## 3. Persistence decision
ADR-001 selects SQLite behind persistence/repository boundaries, with `@capacitor-community/sqlite` as the implementation candidate, subject to a CI/device compatibility gate. Do not install the latest plugin version blindly: select a release compatible with the project's Capacitor 6 stack.

Fallback: if compatibility, transactions, migrations or reliability fail validation, reassess before implementation; IndexedDB may be temporarily retained behind an abstraction.

## 4. Proposed module boundaries
- `app/`: bootstrap, navigation and application lifecycle
- `ui/`: screen rendering, dialogs and input handling
- `services/`: workflow orchestration
- `domain/`: validation, domain invariants and operation definitions
- `repositories/`: persistence contracts and domain-focused data access
- `database/`: selected storage adapter, transactions and migrations
- `migration/`: schema migration and prototype transition tooling as needed
- `shared/`: reusable non-domain utilities

Do not mechanically split files before identifying responsibilities and tests.

## 5. Stage 1 work packages

### WP1 — Establish baseline and test infrastructure
- Inventory supported prototype workflows and record baseline behaviour.
- Establish build reproducibility and CI status.
- Introduce a test framework suited to this JavaScript project.
- Add tests for important operations before refactoring.
- Establish branch-only workflow and rollback boundaries.

### WP2 — Persistence decision and data architecture
- ADR-001 records SQLite as the target, subject to compatibility gate.
- Confirm storage lifecycle and schema migration strategy.
- Define repository contracts and transaction boundaries.
- Define integrity validation and backup/export approach.

### WP3 — Modular application boundaries
- Introduce bootstrap and module boundaries incrementally.
- Extract persistence access from UI functions.
- Separate UI event handlers from domain operations.
- Keep UI/design changes out of this package unless required.

### WP4 — Stable identity and integrity foundations
- UUID policy for new records.
- Explicit relationship IDs; avoid name-based relationships.
- Validate operations before mutation.
- Atomic operations for related domain changes.
- Append-oriented audit and correction operations.
- Idempotency primitives for future synchronization.

### WP5 — Clean prototype transition
- No legacy user-record migration is required.
- Inventory prototype behaviour and decide what to preserve/redesign against the blueprint.
- Define the clean initial schema and versioned schema migration mechanism.
- Isolate/remove demo seed records from production-facing defaults as appropriate.
- Validate schema and relationships; never silently discard data in future migrations.
- Ensure backup/export and recovery are designed before release.

### WP6 — Quality gates
- Automated unit/integration tests.
- Clean-install test.
- Schema-upgrade/migration test.
- Persistence/restart test.
- Transaction-failure tests.
- Android CI build.
- Physical-device smoke test before claiming functional verification.

## 6. Stage 1 safety rules
- Work only on `homemeds-2.0-architecture`; never modify `main`.
- No cloud services/auth/sync during Stage 1.
- Do not change signing secrets or identity.
- Keep each package reviewable and independently revertible.
- Validate against prior workflows and clearly distinguish build, test and device evidence.

## 7. Immediate next step
Run a compatibility spike for the pinned Capacitor 6-compatible SQLite plugin in the generated Android CI workflow. In parallel, begin WP1 baseline/test harness planning; do not migrate app code into SQLite until the compatibility and transaction gates are proven.
