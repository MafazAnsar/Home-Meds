# Stage 1 — Technical reconnaissance and implementation plan

**Status:** Proposed implementation plan; no application changes yet
**Branch:** `homemeds-2.0-architecture`
**Baseline:** Commit `330d88c9bb423494d0378e00fcabe82446b4c271`

## 1. Verified current structure

The branch is a lightweight Capacitor 6 application:
- `index.html` — UI markup and inline event handlers.
- `src/app.js` — UI rendering, domain operations, and IndexedDB persistence in one file.
- `src/styles.css` — styles.
- `package.json` — Capacitor dependencies, but no scripts, test framework or committed lockfile.
- `capacitor.config.json` — app ID, web directory and app name.
- `.github/workflows/build-homemeds2.yml` — CI assembles `www`, installs packages, generates Android project, syncs and builds signed debug APK.
- Android native project is generated by the workflow and is not committed in this branch's current tree.
- Database name `home-meds-2`, schema version 4, IndexedDB stores presently include medicines, doseEvents, profiles, stockTransactions, doseAudit, inventoryItems, prescriptions, doctorProfiles and inventoryTransactions.

## 2. Findings and constraints

### 2.1 Current coupling
The current JS combines database access, rendering, UI event binding, business operations, migration logic and user prompts. This is a migration risk; extracting modules must be incremental and behaviour-preserving.

### 2.2 Existing records and data risk
The application already stores operational data locally. A new database cannot be introduced without an explicit, tested migration/export strategy. Do not reset, delete or overwrite the current IndexedDB database during development.

### 2.3 Build pipeline
The workflow generates Android from Capacitor on CI. Any native plugin must be compatible with this generated-project workflow and must be installed/configured during CI. Preserve signing secrets and signing configuration.

### 2.4 Current test gap
No test framework or test scripts were found in the package manifest. Stage 1 must add repeatable test infrastructure and build/test gates. A successful APK build alone does not verify application behaviour.

## 3. Database evaluation

### Candidate A — SQLite via a Capacitor-compatible plugin
**Potential advantages**
- Relational schema and constraints
- Transactions across related domain records
- Explicit indexes and migrations
- Better fit for transactional domain workflows and future reconciliation

**Risks / work required**
- Native plugin compatibility and Android build verification
- Plugin lifecycle and generated Android build integration
- Existing IndexedDB migration path
- Data export/import and corruption/recovery strategy
- Test coverage for transactions and schema upgrades

### Candidate B — IndexedDB
**Advantages**
- Existing implementation and no additional native plugin
- Browser-compatible
- Lower immediate migration risk

**Risks**
- Referential integrity and relational constraints must be implemented in application logic
- Transaction boundaries and domain consistency become harder to maintain across stores
- Existing coupling to IndexedDB makes architecture changes harder

### Preliminary recommendation
Evaluate SQLite via a Capacitor-compatible SQLite plugin as the preferred long-term Android local database. This is **not yet an implementation decision**. Confirm compatibility, transaction behaviour, migration/export capability, plugin maintenance and CI integration before committing to it.

If the evaluation fails any critical requirement, retain IndexedDB temporarily behind a repository abstraction while documenting the trade-offs.

## 4. Proposed module boundaries

The exact implementation can evolve, but responsibilities should be separated:

- `app/`: bootstrap, navigation and application lifecycle
- `ui/`: screen rendering, dialogs and input handling
- `services/`: orchestration of application workflows
- `domain/`: validation, domain invariants and operation definitions
- `repositories/`: persistence contracts and domain-focused data access
- `database/`: selected storage adapter, transactions and migrations
- `migration/`: legacy IndexedDB import and migration tooling
- `shared/`: reusable non-domain utilities

Do not mechanically split files before identifying responsibilities and tests. Introduce modules in small, coherent increments.

## 5. Stage 1 implementation work packages

### WP1 — Establish baseline and test infrastructure
- Document current supported workflows.
- Establish build reproducibility and CI status.
- Introduce a test framework suited to the current JavaScript project.
- Add tests for the most important existing operations before refactoring.
- Establish a branch-only workflow and explicit rollback boundaries.

### WP2 — Persistence decision and data architecture
- Complete SQLite/plugin evaluation.
- Confirm storage lifecycle and migration strategy.
- Define repository contracts and transaction boundaries.
- Define schema migration and integrity validation approach.
- Record the decision in an ADR before database implementation.

### WP3 — Modular application boundaries
- Introduce application bootstrap and module boundaries.
- Extract repository/persistence access from UI functions.
- Separate UI event handlers from domain operations.
- Keep UI/design changes out of this package unless required.

### WP4 — Stable identity and integrity foundations
- UUID policy for new records.
- Explicit relationship IDs; avoid name-based relationships.
- Validate operations before mutation.
- Atomic operations for related domain changes.
- Append-oriented audit and correction operations.
- Idempotency primitives for future synchronization.

### WP5 — Legacy data migration and preservation
- Inventory current records and store shapes.
- Design migration with dry-run/reporting.
- Preserve doses, audit records, profiles, medicines, prescriptions, doctor records, inventory and attachments where present.
- Validate record counts and relationships.
- Never silently discard unsupported or malformed data.
- Keep rollback/export safety available.

### WP6 — Quality gates
- Automated unit/integration tests.
- Clean-install test.
- Upgrade/migration test.
- Persistence/restart test.
- Transaction-failure tests.
- Android CI build.
- Physical-device smoke test before claiming functional verification.

## 6. Safety rules for Stage 1

- Work only on `homemeds-2.0-architecture`; never modify `main`.
- Do not delete the legacy database.
- Do not reset user data.
- Do not change app signing secrets or signing identity.
- Do not add cloud services or authentication.
- Do not expand feature scope.
- Keep each work package reviewable and independently revertible.
- Validate changes against prior workflows and state exactly what was and was not tested.

## 7. Immediate next step

Complete the SQLite/plugin compatibility evaluation and formalise the database ADR. Then begin WP1 with a baseline test harness and regression tests before structural refactoring.
